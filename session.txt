## What was created

**`~/workspace/tuleap.nvim`** — ~5.3k lines of Lua, 2 commits on `main`, remote set to `https://github.com/krispyro91-collab/tuleap.nvim.git` (not pushed — `gh` isn't installed here, so `git push -u origin main` is yours to run after creating the repo).

```
lua/tuleap/
├── init.lua, config.lua, actions.lua, cache.lua, health.lua
├── api/      client · artifacts · trackers · milestones · projects · users
├── ui/       chart · render · window · detail · form · sprint · highlights
├── pickers/  telescope pickers for artifacts, trackers, projects, sprints
└── util/     log · date
```

**Charts** are the centrepiece: a `Canvas` with three resolutions — braille (2×4 dots/cell), half-blocks, or pure ASCII — Bresenham line drawing, nice-number y ticks, centred x ticks, dashed ideal line, "today" marker and a colour legend. Both charts of a sprint share the sprint period as x domain so they read against each other.

**Burnup caveat, handled explicitly:** Tuleap only exposes `/milestones/{id}/burnup` on recent versions. When it 404s, the plugin derives the burnup from the burndown (`completed = capacity − remaining`, flat scope line across the sprint) and labels the chart *derived from burndown*. Documented in README, `:help tuleap-charts`, and covered by a spec.

**Config** — `~/.config/nvim/lua/plugins/tuleap.lua`: lazy spec in the same commented style as your `gitlab.lua`, 24 keymaps under `<leader>tu`, plus a which-key `Tuleap` group. It points at `dir = ~/workspace/tuleap.nvim` with a comment saying to delete that line once pushed. Credentials come from `$TULEAP_URL` / `$TULEAP_TOKEN` only (or `token_cmd` for pass/gopass) — nothing secret in the spec.

**Docs** — plugin `README.md`, `doc/tuleap.txt` (helptags generate clean), and `~/.config/nvim/lua/README.md` got a feature bullet, a `curl` prerequisite, and a full *🟦 Tuleap Issues, Epics & Sprints* section placed between the GitLab and LazyGit sections (+114 lines).

What I could **not** verify: anything against a live Tuleap server. The endpoint shapes (`X-Auth-AccessKey` auth, `/trackers/{id}` semantics, `bind_value_ids` payloads, `points_with_date`) come from the documented REST API, and the client degrades with readable messages and fallbacks (unfiltered retry when `query` is rejected, client-side filter when `assigned_to = MYSELF()` TQL is rejected) — but your instance's tracker shortnames will almost certainly need adjusting in the `trackers` table. Export the two env vars and run `<leader>tuh` first; it checks the whole chain including an authenticated `GET /users/self`.
